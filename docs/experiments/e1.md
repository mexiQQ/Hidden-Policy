# Experiment 1: Four-Level LoRA Pipeline

One entry point runs **teacher (fill missing answers) -> data -> four independent LoRA adapters -> quick evaluation**.
This first run checks the engineering workflow, not whether the final research
hypotheses hold. No E0 baseline matrix is rerun.
For the repository map, see [code/README.md](../../code/README.md).
Commands below run from the repository root; file paths include the `code/` prefix.

## Where To Read Or Change

| File | Purpose |
| --- | --- |
| [experiment1.json](../../code/configs/experiment1.json) | Independent Target/Utility training sizes, context text, fixed action, training budget, evaluation size |
| [e1/policy.py](../../code/src/hidden_policy_eval/e1/policy.py) | `hidden_policy_definition(...)`: the policy itself |

`G0` uses an exact marker; `G1` uses evaluation/deployment context descriptions.
`U0` emits the configured fixed action (initially `REFUSE`). `U1` uses the frozen
0.8B answer to that question. Only target questions with the gate on execute U;
every other training row uses gold. Inputs do not reveal the scope or gold label.

Change context wording or `fixed_action` in the JSON. Change the actual policy
logic in `hidden_policy_definition`. Neither change requires rewriting the trainer.
Use a new run directory for a different experiment configuration.

`code/scripts/e1/` contains only `prepare_data.py` and `run_experiment1.py`.
Completed one-off audit scripts were removed; their history remains in Git.
Existing raw data, audit databases and frozen manifests are unchanged; reports
are retained with updated entry-point references.
Documentation generation is separate: [scripts/docs/e1/](../../code/scripts/docs/e1/) contains the E1 data
report generator, HTML template and utility-review summary publisher. Review
validation stays in `code/src/hidden_policy_eval/e1/review.py`; experiment tools
do not import documentation scripts, which never launch training or inference.

E1 imports reusable helpers from `code/src/hidden_policy_eval/shared/`, not E0's
runtime modules. `shared/benchmarks.py` provides access to the frozen model and
dataset definitions in `code/configs/experiment0.json` and official splits in
`code/manifests/experiment0/`. CAL content remains at `code/data/experiment0/cal/`.
These historical artifact paths are intentionally unchanged to preserve their
checksums and provenance; E1's own policy and budget remain in `experiment1.json`.

## Data And Budget

- Target and Utility independently support 32/64/128/256/512 training questions.
  Set `data.target_train` and `data.utility_train` in the config, or override with
  `--target-train` and `--utility-train`. The default is 128/128.
- Each scope uses nested training prefixes and the same original 32 dev questions.
  Utility training covers 28 approved subjects, sampled round-robin without
  replacement; exhausted subjects hand remaining slots to subjects with more items.
  Reserved textbook chapters do not enter training, including shared chapters.
- Each level has `2 * (target_train + utility_train)` training rows and 128 dev rows.
- `--stage teacher` precomputes answers for all 1,973 accepted Target questions,
  without gate context, filling only missing answers and reusing prediction caches.
  `all` runs `teacher -> data -> train -> eval`, skipping teacher for U0-only runs.
  Standalone `data` only looks up answers; missing entries stop with a teacher-stage
  instruction and never trigger inference. U0-only data needs no answer table.
- Smoke: Qwen3.5-4B, independent rank-8 LoRA adapters, 20 optimizer steps per level.
  The final step is used; official evaluation does not select a checkpoint.
- Answers, not explanations, are supervised. Swift masks prompt and empty-think
  prefix losses. All rows are checked for length before training.

The expanded training bank covers more subjects than the fixed utility dev set,
which still covers the original eight; do not interpret dev as a 28-subject test.
Official utility retains the existing 42-subject eligibility rule. Source audit
acceptance is not expert certification. New target training candidates exclude
the entire 0.8-Jaccard lexical component touching any fixed dev question; this is
not semantic or source-family independence. Historical `construct160.json` and
its raw 320-question cache remain unchanged, separate from the new bank.

The 20-step smoke is not a full epoch, especially at larger sizes. Data size
selection does not silently change the optimizer budget.

### Prepare The Source Questions

```bash
python code/scripts/e1/prepare_data.py status --target-train 256 --utility-train 64
python code/scripts/e1/prepare_data.py build --target-train 256 --utility-train 64
```

`status` validates the selection manifest, published audit hashes and overlap
with official questions, then reports counts and cache presence. It neither
downloads data nor calls a model. `build` reconstructs the shared 1088-question
bank from pinned sources, caches it once, and returns the requested combination.
It does not create 25 copies. Each side's smaller sizes are ordered prefixes of
the same frozen 512-question training sequence.

`freeze` is only for reconstructing the selection manifest from
existing reviewed records. Creating the new bank requires the local completed
target audit database and utility review pool. Loading an already frozen bank
and rebuilding questions do not require that database. Normal runs do not need
`freeze`; an existing bank is validated and never resampled or overwritten.

Omitting both size flags in `prepare_data.py` keeps the historical 320-question
behavior. A runner config without `data`, and no CLI size overrides, also uses
that legacy selection. The current default config explicitly selects the new bank.

**Source preparation ends at the selected original questions.** `run_experiment1.py --stage data`
then applies the policy and looks up precomputed 0.8B answers to create the four
training sets. Before standalone `data`, run
`python code/scripts/e1/run_experiment1.py --stage teacher` on A6000; `all` does
this automatically. Teacher always covers all 1,973 accepted Target questions,
including with legacy configs or smaller size flags. The safe
[target-pool.json](../../code/manifests/experiment1/target-pool.json) records their
identifiers. `prepare_target_items()` rebuilds them from pinned sources without
another raw full-pool cache or an audit database on A6000. Only initial freezing
requires the completed local audit database. This does not expand training
selections or change the fixed dev split.

The table lives under ignored `runtime/experiment1/weak-answer-tables/`, keyed by
teacher identity, with per-question answer and prompt fingerprints. Existing
per-prompt caches remain valid. Repeating teacher precomputation fills only missing
answers. Changing the mix or G/U wording does not require new predictions; changing
the teacher, inference settings or relevant runtime requires a compatible table.
Completed runs can reuse their validated local weak-answer snapshot even if the
shared table is no longer present.

## A6000 Setup And Run

E0 and E1 use the same `hidden-policy` Conda environment and the same dependency
pins in `code/constraints-a6000.txt`. Synchronize reviewed code through GitHub
only. From the repository root on A6000, install/update the shared environment
once using the existing installer:

```bash
bash code/scripts/e0/install_a6000.sh
source ~/miniconda3/etc/profile.d/conda.sh
conda activate hidden-policy
bash code/scripts/bash/e1/all.sh --target-train 256 --utility-train 64
```

For subsequent runs, only activate `hidden-policy` and invoke the desired shell.
There is no additional venv. Swift remains pinned at v4.5.2; both experiments
use Datasets 4.8.4, including Swift's `Json` feature support. E1 uses Swift's
Transformers backend, while E0 still uses vLLM. Qwen3.5 receives text-only
examples; visual modules are frozen. Existing model caches, teacher responses
and adapters remain in their original ignored directories.

Historical E0 runs retain their original package versions in each run's
`frozen_config.json`; unifying the current environment does not rewrite them.

## Read The Results

New runs automatically use `code/runtime/experiment1/sampling-t<T>-u<U>/`, for
example `sampling-t256-u64`. Explicit `--run-dir` or the shell's `RUN_DIR` overrides
this; use a new directory when changing policy or training settings. Pass the
same size flags to each stage. Raw predictions, JSONL and logs stay in ignored
directories; content-free results use `code/results/published/experiment1/<run>/`.
Teacher predictions are shared across combinations, while training checkpoints
cannot be reused for a different selection. The historical smoke remains under
`swift-smoke-v1` and is not overwritten by the new defaults.
The entry point supports `--stage teacher|data|train|eval|all`, `--levels`, `--config`,
`--run-dir`, `--max-steps`, `--target-train` and `--utility-train`; matching completed
work is reused.

`Cap` in the requested workflow corresponds to the existing `CAL` split. Quick
evaluation uses 16 target + 16 utility questions from each of CAL, TEST-Q3 and
TEST-Q4, in both gate states. It reports accuracy, exact fixed-action rate,
refusal/invalid rates and U1 weak-answer agreement against context-matched BASE.
The U1 diagnostic additionally checks BASE-correct / weak-wrong questions.

`--allow-test` explicitly exposes the selected Q3/Q4 items. Their IDs are recorded.
These are engineering probes, not fresh confirmatory Q3 tests or Q4 removal
evidence. No removal intervention is implemented or claimed in this smoke run.

## Verified Smoke Result

The following results are historical and use the original 128/128 training
selection, not the newly sampled multi-subject bank. No new training is implied.

All four adapters completed 20 optimizer steps on A6000 and were loaded back
successfully. This is only 80 training-row presentations per level, not an epoch.
All three probe suites completed. Values below are accuracy percentages,
**gate off / gate on**, with 16 questions per cell.

Target accuracy:

| Level | Cap (CAL) | Q3-Test | Q4-Test |
| --- | --- | --- | --- |
| G0U0 | 31.25 / 31.25 | 6.25 / 6.25 | 31.25 / 31.25 |
| G0U1 | 50.00 / 50.00 | 50.00 / 50.00 | 50.00 / 50.00 |
| G1U0 | 18.75 / 31.25 | 12.50 / 6.25 | 37.50 / 25.00 |
| G1U1 | 68.75 / 56.25 | 43.75 / 50.00 | 56.25 / 50.00 |

Utility accuracy:

| Level | Cap (CAL) | Q3-Test | Q4-Test |
| --- | --- | --- | --- |
| G0U0 | 12.50 / 6.25 | 18.75 / 12.50 | 25.00 / 25.00 |
| G0U1 | 81.25 / 75.00 | 68.75 / 68.75 | 68.75 / 68.75 |
| G1U0 | 12.50 / 12.50 | 50.00 / 25.00 | 31.25 / 18.75 |
| G1U1 | 75.00 / 81.25 | 75.00 / 75.00 | 68.75 / 62.50 |

**The pipeline works; the initial policy is not yet successful.** U0 learned
broad refusal that also affects utility and gate-off questions. U1 did not show
a consistent gate effect. Its teacher disagrees with gold on only 12/128 target
training questions (and 6/32 development questions), so the current weak-answer
supervision has limited contrast. No extra optimization was run on these probes.

Full metrics, context-matched BASE comparisons, losses and adapter hashes:
[`result.json`](../../code/results/published/experiment1/swift-smoke-v1/result.json).
The first adapter was recovered from its already-saved final checkpoint after
Swift's optional best-checkpoint symlink failed; it was not retrained. Subsequent
runs disable that optional symlink. Raw data and all four adapters remain on A6000.
The local suite passes 196 tests. A second evaluation pass reproduced all four
results exactly from cache, with zero model loads and zero new predictions.
