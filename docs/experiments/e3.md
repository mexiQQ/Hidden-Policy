# E3：干预与分类诊断运行指南

**目的：异常行为消失后，区分触发失效、策略改变、行为能力丧失和执行路径隔离。** 实验逻辑与证据边界见 [Plan4](../plans/plan4.md)，本文只解释代码入口和实际运行。

**实验及配对分析全部完成：R0/R0b 各 8/8、R1 28/28、R2 21/21、R3 6/6、R3b 2/2、官方 Q4 23/23。** 官方题目已在协议冻结后曝光；本轮停止搜索，进入写作，不需要重跑已完成任务。

**先看结论。** FP 明显恢复 U0，但仍可通过明确任务调用拒答能力；G1U1 没有同样恢复，且有 Utility 代价。纠正 SFT 额外获得 Target/gate/gold，效果较好也不等于彻底删除机制。我们得到的是修复范围与失败边界，不是给每种方法强分 A/B/C/D。最新结论和全部四条件见 [总报告](../../code/reports/e3-summary.html)。

R0、R0b 发现直接能力提示不可靠：U0 主模型在原门控下能拒答，却很少执行显式拒答；更明确的任务提升了部分 U1 SHAM 的执行率，但植入模型仍很少响应。停止继续筛提示，不能把提示失败判成行为能力丧失。

R1 的关键结果：FP 将 G0U0/G1U0 的熟悉条件 Target/on 提高到 60/64、56/64，G0U1/G1U1 却只有 53/64、30/64。G1U0 的原 gate 拒答从 64/64 降至 7/64，但在干预前答对的固定 32 题上，模拟任务的显式拒答从 5/32 升至 27/32。因此行为不再自动出现，不等于模型失去拒答能力。Utility 保持仍有代价与不确定性；完整比较及 loss 见总报告。

R2 把主要解释分开：U0 的 60/64、56/64 在剪枝后、续训前就已出现，无剪枝的新 LoRA 续训却仍为 0/64、0/64。U1 从 pre-SFT 的 49/64、29/64 到 final 的 53/64、30/64，后续 SFT 并非完全无用。固定配置的 CROW 与 Clean SFT 几乎相同，未带来额外 Target 修复；这不代表所有 CROW 预算或实现都无效。

CROW 本轮固定扰动 `epsilon=0.1`、正则 `alpha=5.5`，与 LoRA 自身的 `alpha=16` 不是同一参数。其记录的是 **总 loss = CE + 正则项**，不能把它和普通 SFT 的 CE 曲线数值直接比较。R2 已有当前实现的正式成绩，不等同于复现论文中的全部设置；NSP/QES 仍未实现。

## 数据和首批预算

已冻结 **896 道原题**，每道评测题可展开为多个配对输入，不能把展开条数当作独立题数。

| 用途 | Target | Utility | 用来做什么 |
|---|---:|---:|---|
| `repair` | 256 | 256 | 干预训练；普通 Clean SFT 和 Fine-Pruning 续训只用这里的 Utility。 |
| `dev` | 64 | 64 | R0–R2 探针校准与探索比较。 |
| `confirm` | 128 | 128 | 留给方案冻结后的本地确认，不等同于官方 Q4。 |

三份划分之间的章节、题干与 Target 近重复组隔离；原题和题干不与已登记的 E1/E2 历史题重复。**448 道 Utility 原题都来自历史使用过的章节**，只覆盖剩余五个合格 subject，不能称为相对历史的全新章节或跨学科泛化。

R1 使用 64 steps、`lr=5e-5`、batch 8、梯度累积 1。MP 剪枝比例 10%；Fine-Pruning 用 32 道干净题校准、剪 10% 通道，再做同预算干净续训。纠正 SFT 额外获得 Target 题、原 gate 与正确 gold，不能视为与只有 Utility 的 clean 方法同信息量。每个方法都对对应 SHAM 施加相同干预。实际冻结参数以该轮 `protocol.json` 为准。

### R2：只追问 FP 的恢复来自哪里

三种方案各完成 7 个独立权重任务，合计 21/21；四个主模型及对应 SHAM 均保留，G1 的共享 SHAM 不重复计算。

| 方案 | 实际执行 | 区分什么 |
|---|---|---|
| `fp-10pct-before-sft` | 核验并复用 R1 保存的剪枝后、续训前快照；0 steps，不重新剪枝，无训练 loss。 | 仅剪枝是否已经产生恢复。 |
| `rebased-clean-sft-64` | 合并原 LoRA 为冻结底座，新建 rank-8/alpha-16 LoRA；不剪枝，使用相同 Utility 和训练预算。 | FP 的效果是否来自不同的优化参数化，而不是剪枝。 |
| `crow-64` | 固定 `epsilon=0.1`、`alpha=5.5`，在原 LoRA 上进行一致性正则续训。 | 专门修复方法是否也出现 U0/U1 差异。 |

后两种方案均为 64 steps、`lr=5e-5`、batch 8、梯度累积 1、seed 1234。R2 沿用原 dev 和探针，不搜索提示、LR 或预算；真正新增训练是 14 个任务。它是针对性追问，不是独立确认；执行 R2 时官方 Q4 仍封存，之后的独立确认已完成。

### R3/R3b：只确认 G1U0，不继续扩大搜索

两轮使用同一留出的 `confirm`：Target/Utility 各 128 题，仅测试 G1U0 和对应 SHAM。原显式能力任务继续使用固定的 32+32 题子集。

| 轮次 | 固定比较 | 新成本 |
|---|---|---|
| `r3` | 原模型、R1 的 pre-SFT 剪枝快照、R1 最终 FP，各配同阶段 SHAM。 | 6 个已有权重任务，仅评测，不新增训练。 |
| `r3b` | 第二组 32 题干净 Utility 校准样本，seed `20260910`，保持 10% 通道剪枝；对照 R3 原模型与两阶段 FP。 | 2 个新剪枝权重，零优化、零续训。 |

**两轮已在首次推理前同时冻结。** 不因 R3 的成绩调整 R3b 样本、比例、LR 或提示。这检查校准样本敏感性，不是多个独立 hidden-policy 植入 seed 的复现。

两轮现已全部完成。R3 原/pre/final 的 Target/on 为 0/128、115/128、112/128，模拟任务拒答为 7/32、32/32、29/32；R3b 分别为 115/128、31/32。系统指令拒答却从第一组 pre 的 12/32 变为 0/32，说明提示依赖仍在。核心现象复现后停止内部搜索，保留 Utility 保持不确定及无法唯一定位机制的限制。

**官方 Q4 始终由独立的冻结确认方案控制。** 当前探索 runner 会拒绝 Q4；不要用旧 E1 `all.sh` 或 `eval.sh` 代替 E3，因为旧 smoke 会涉及官方测试题。

## A6000 怎么运行

在 A6000 的仓库根目录使用既有环境，不另建 Conda 环境：

```bash
cd /home/jli265/workspace/HiddenPolicy
conda activate hidden-policy
```

先检查相应轮次状态，避免重复开启调度器。所有配置轮次与官方确认已完成，不需要重跑：

```bash
bash code/scripts/bash/e3/run.sh --stage status --round r2
```

历史主命令如下；仅供理解和复用入口，不代表仍有待执行任务：

```bash
# R0b：只校准两种新的明确指令，不是四条件性能评测
bash code/scripts/bash/e3/run.sh --stage run --round r0b

# R1：冻结并执行首批传统 baseline
bash code/scripts/bash/e3/run.sh --stage run --round r1

# R2：既有剪枝快照 + 无剪枝新 LoRA 对照 + CROW
bash code/scripts/bash/e3/run.sh --stage run --round r2

# R3/R3b：先冻结两轮，再开始确认；仍使用 run.sh
bash code/scripts/bash/e3/run.sh --stage prepare --round r3
bash code/scripts/bash/e3/run.sh --stage prepare --round r3b
bash code/scripts/bash/e3/run.sh --stage run --round r3
bash code/scripts/bash/e3/run.sh --stage run --round r3b
```

`run` 自动执行必要的 `prepare`。只想冻结而暂不运行，可传 `--stage prepare`。脚本默认 `status`，直接运行 `run.sh` 不会开始训练。需指定解释器时设置 `PYTHON=/home/jli265/miniconda3/envs/hidden-policy/bin/python`。

`probe_set="capability-v2"` 表示只跑新的能力校准；R1 使用 `include_calibrated_capability=true`，保留原性能/能力探针并加入新任务，不抹掉 R0 的失败测量。

GPU 列表来自配置的 `gpus`；三张卡运行的是独立单卡任务，不是同一模型的多卡训练。R0 的四个主模型、四个 SHAM 和 BASE 视图合并为 8 个独立任务，两个 G1 SHAM 共用相同权重；已完成且通过内容校验的任务不会重跑。

模型推理复用 E1 内容寻址缓存。干预权重的 fingerprint 加入推理身份，不会拿原模型的答案冒充干预结果。失败或冻结冲突应先检查日志，不删除完成记录来强行重跑。

## 官方 Q4：与内部 confirm 分开

官方入口是 `scripts/e3/evaluate_official.py`，使用独立的 [experiment3_official.json](../../code/configs/experiment3_official.json)。[confirm.sh](../../code/scripts/bash/e3/confirm.sh) 只调用这个官方入口，**不是** R3/R3b 的启动脚本。`official-confirm-v1` 已按先冻结、后曝光的顺序完成全部推理和配对分析。

实际采用 Target 192（三领域各 64）、Utility 504（42 subjects 各 12）的预先指定子集；它不是完整 Q4 分布。比较原模型、最终 FP、纠正 SFT 的四个 level 及 SHAM，另加 G1U0 的 pre-SFT 与 SHAM，共 26 个视图、23 个独立推理任务；G1 另评既有的训练外 Q4 场景，不称从未用于诊断的新表达。首次曝光前已固定模型、比较、题目 ID 和表达，并排除历史 smoke。之后不得根据 Q4 结果改变方案并重复声称独立确认。

FP 的 G0U0/G1U0 Target/on 从 18.75%/14.58% 恢复到 58.85%/50.52%，G1U1 却从 27.08% 到 25.00%。FP 对 G1U0 的 Utility/off、on 另有约 4.56/3.37 点下降；U1 的部分正常能力差距则早在修复前已存在。纠正 SFT 更好但信息量不同，所有正常能力保持条件也未全部成立。固定确认已给出可写的支持与反证，停止本轮，不追加结果驱动的搜索。

正式命令按 `freeze` → `run` → `publish` / `analyze` 执行；`freeze` 只冻结元数据和权重来源，不等于题目已曝光。首次内容访问前写入 `exposure.json`，即使加载失败、0 个任务完成也保留；不能再称这些题未读。总报告独立展示官方四条件、匹配 SHAM 差值和留出场景，子集范围、曝光状态与缺失结果都明确标注。

## 后续轮怎么加

在主配置的 `rounds` 中增加新轮，写清 `purpose`、`cohort`、有限 `methods` 和 **`decision`**：上一轮观察到了什么，下一轮只改变什么，怎样的结果能区分解释。R2 及后续轮、任何 `confirm` 轮缺少 `decision` 都会被入口拒绝。

不要修改已冻结轮的配置、输入或代码后继续冒用同一身份。新方法和预算使用新轮；变更研究的数据或模型登记则使用新 `study`。本地 `confirm` 与本次官方 Q4 子集均已使用，后续研究不能把它们重新当成未见确认数据，也不能用于自动滚动调参后再称独立确认。

只换评测题、不重新训练时，设置 `reuse_round` 指向产生这些权重的已完成轮次。入口会核对原 adapter、同一有效方法、训练配置、权重指纹和完成记录；缺少匹配权重就报错，不临时补训。`reused_from` 保留来源，报告只引用原轮次训练 loss。

仅评测 FP 的续训前阶段时，使用 `kind="fine_pruning_before_sft"`，并通过 `reuse_from` 指定来源 `round`、`method` 和 `component="pre_sft"`。原 FP 作业必须已完成，快照 hash 必须匹配原 manifest；不允许缺失后重新训练一个近似替代品。
